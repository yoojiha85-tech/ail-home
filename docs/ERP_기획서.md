# 허니문 여행사 ERP 기획서
### 상담기록 → 견적서 → 예약 → 계약서 → 예약기록 → 예약의뢰서 → 정산 통합 시스템

작성일: 2026-09-19 · 대상: (주)아일항공여행사 허니문 사업부

---

## 1. 목표

현재 상담-견적-예약-계약-정산이 **엑셀·수기·메신저로 분산**되어 있어 다음 문제가 발생합니다.

- 상담 이력이 담당자 개인 자료에만 남아 인수인계·재상담 시 정보 유실
- 견적서 버전 관리가 안 되어 "고객에게 어떤 금액을 보냈는지" 혼선
- 예약 확정 후 계약서·예약의뢰서(항공/리조트 발주)가 별도 문서로 관리되어 누락 위험
- 정산 시 원가·판매가·수수료를 재계산해야 해서 시간 소모 크고 오류 발생

**ERP의 핵심 목표**는 고객 1건의 문의가 들어온 순간부터 정산 완료까지 **하나의 데이터(예약 건)로 끝까지 연결**되어, 상담원이 반복 입력 없이 다음 단계로 넘어갈 수 있게 하는 것입니다.

---

## 2. 전체 업무 흐름 (End-to-End)

```
① 상담기록 → ② 견적서 → ③ 예약(가예약) → ④ 계약서 → ⑤ 예약기록(확정) → ⑥ 예약의뢰서(발주) → ⑦ 정산
```

| 단계 | 이 단계에서 하는 일 | 담당 | 상태값(예시) |
|---|---|---|---|
| ① 상담기록 | 고객 문의 접수, 희망 목적지/예산/일정/인원 기록 | 상담원 | 신규 → 상담중 → 견적대기 |
| ② 견적서 | 상담 내용 기반 항공+리조트+객실+식사플랜 견적 산출, 고객 발송 | 상담원 | 작성중 → 발송완료 → 수정요청 |
| ③ 예약(가예약) | 고객이 견적 수락 → 항공/리조트 좌석·객실 임시 확보(Hold) | 상담원 | 가예약 → 확정대기 |
| ④ 계약서 | 여행계약서(약관, 취소규정, 결제조건) 발행 및 서명 | 상담원/고객 | 발송 → 서명완료 |
| ⑤ 예약기록 | 계약 완료 건을 정식 예약으로 전환, 예약번호 부여 | 시스템 자동 | 확정 |
| ⑥ 예약의뢰서 | 항공사/리조트/랜드사에 발권·바우처 요청 문서 발송 | 예약팀 | 의뢰발송 → 컨펌수신 |
| ⑦ 정산 | 원가/판매가/수수료 계산, 입금·출금 매칭, 마진 확정 | 경리/관리자 | 정산대기 → 정산완료 |

핵심은 **③~⑦이 모두 "하나의 예약 건(Booking ID)"에 연결**된다는 점입니다. 즉 상담기록에서 시작된 데이터가 견적서 번호, 예약번호, 계약서번호, 정산번호로 옆으로 계속 이어집니다(엑셀로 비유하면 "고객관리" 시트의 한 행이 "견적", "예약", "계약", "정산" 시트로 고유번호를 통해 서로 연결되는 구조입니다).

## 3. ERP 모듈 구성 (7개 모듈 + 2개 마스터 모듈)

### 업무 모듈
1. **CRM/상담관리** – 고객 정보, 상담 이력, 문의 채널(전화/카톡/홈페이지)
2. **견적관리** – 견적서 작성, 버전 관리, 고객 발송 이력
3. **예약관리** – 가예약/확정예약, 좌석·객실 Hold 상태 추적
4. **계약관리** – 전자계약서, 약관·취소규정, 서명 상태
5. **예약의뢰(발주)관리** – 공급사(항공사/리조트/랜드사)별 발주서, 컨펌 회신 관리
6. **정산관리** – 원가/판매가/마진, 입금·출금, 미수금·미지급금
7. **리포트/대시보드** – 상담원별 실적, 목적지별 판매량, 월별 매출·마진

### 마스터 데이터 모듈 (다른 모듈이 참조하는 기준 정보)
8. **상품 마스터** – 목적지, 리조트, 객실타입, 시즌, 요금표, 취소규정
9. **공급사/파트너 마스터** – 항공사, 랜드사, 리조트 담당자·연락처·정산조건

## 4. 데이터베이스 설계 (핵심 테이블)

> 참고: Table=엑셀 시트, Row=한 줄의 데이터, Column=항목, PK=고유번호, FK=다른 표와 연결하는 연결고리 라고 생각하시면 됩니다.

### 4-1. 핵심 테이블 관계도

```
customers(고객)
   └─< consultations(상담기록)
           └─< quotes(견적서) ─< quote_items(견적상세: 항공/리조트/객실/식사)
                   └─< bookings(예약)
                           └─1 contracts(계약서)
                           └─1 booking_confirmations(예약기록/확정)
                           └─< supplier_requests(예약의뢰서) ─> suppliers(공급사)
                           └─1 settlements(정산) ─< payments(입출금내역)

products_resorts / room_types / seasons / rate_plans   ← 견적/예약이 참조하는 마스터 데이터
```

### 4-2. 테이블별 주요 항목

| 테이블 | 주요 컬럼(항목) | 설명 |
|---|---|---|
| `customers` | 고객ID(PK), 이름, 연락처, 예식일, 유입경로 | 최초 문의 고객 |
| `consultations` | 상담ID(PK), 고객ID(FK), 상담일시, 희망목적지, 예산, 인원, 상담메모, 담당자 | 상담 이력 누적(여러 건) |
| `quotes` | 견적ID(PK), 상담ID(FK), 버전번호, 총금액, 유효기한, 상태 | 같은 상담에서 여러 버전 견적 가능 |
| `quote_items` | 항목ID(PK), 견적ID(FK), 구분(항공/리조트/객실/식사/옵션), 상품ID(FK), 단가, 수량, 원가, 판매가 | 견적의 상세 라인 |
| `bookings` | 예약ID(PK), 견적ID(FK), 예약번호, 상태(가예약/확정/취소), 출발일, 인원 | 견적이 확정되면 생성 |
| `contracts` | 계약ID(PK), 예약ID(FK), 계약서번호, 약관버전, 서명일, 서명상태, 결제조건 | 전자서명 연동 |
| `booking_confirmations` | 확정ID(PK), 예약ID(FK), 항공PNR, 리조트컨펌번호, 확정일 | "예약기록"의 실체 |
| `supplier_requests` | 의뢰ID(PK), 예약ID(FK), 공급사ID(FK), 의뢰유형(발권/바우처), 의뢰일, 회신상태, 회신번호 | 공급사별로 여러 건 가능 |
| `suppliers` | 공급사ID(PK), 구분(항공사/리조트/랜드사), 담당자, 연락처, 정산조건 | 마스터 |
| `settlements` | 정산ID(PK), 예약ID(FK), 총매출, 총원가, 마진, 정산상태, 정산확정일 | 예약 1건당 1개 |
| `payments` | 결제ID(PK), 정산ID(FK) 또는 예약ID(FK), 구분(입금/출금), 금액, 일자, 방법 | 분할결제/환불 다건 |
| `products_resorts` / `room_types` / `seasons` / `rate_plans` | 목적지, 리조트명, 객실타입, 시즌구간, 시즌별 요금 | 견적 산출의 기준 데이터 |

### 4-3. 설계 시 유의점 (검수 관점)

- **중복 최소화**: 리조트/객실/요금은 마스터 테이블에서 한 번만 관리하고, 견적/예약은 그 값을 참조(FK)만 하도록 설계 → 시즌 요금이 바뀌어도 마스터 한 곳만 수정
- **이력 보존**: `quotes`는 UPDATE가 아니라 버전을 늘려 INSERT (고객에게 "몇 번째 견적을 보냈는지" 추적 가능해야 함)
- **상태값 일원화**: 상담/견적/예약/정산 상태를 각 테이블에 문자열로 흩어놓지 말고, 공통 상태 코드 테이블로 관리 → 리포트 집계 오류 방지
- **안전한 삭제**: 예약이 하나라도 연결된 고객/상품/공급사는 물리삭제(DELETE) 금지, 비활성화(휴면처리) 컬럼으로 대체
- **권한 분리(RLS)**: 상담원은 본인 담당 고객만 조회, 관리자는 전체 조회, 정산 원가/마진 컬럼은 경리·대표만 조회 가능하도록 권한 분리 (고객용 화면에는 원가·마진 절대 노출 금지)

## 5. 화면(UI) 흐름 – 상담원 기준

상담속도를 높이는 것이 최우선이므로, **한 화면에서 다음 화면으로 "이어쓰기"** 가 되도록 설계합니다.

1. **고객 상세 화면** 진입 → 상단에 고객정보, 하단 탭에 [상담이력 | 견적 | 예약 | 계약 | 정산] 순서로 배치
2. 상담 작성 후 **"견적서 만들기" 버튼** 클릭 → 상담 내용(목적지/인원/예산)이 자동으로 견적 화면에 채워짐 (재입력 없음)
3. 견적 확정 후 **"예약 전환" 버튼** → 예약 건 자동 생성, 예약번호 자동 채번
4. 예약 확정 후 **"계약서 발행" / "예약의뢰서 발송" 버튼**이 같은 화면에 나란히 노출 → 클릭 한 번으로 문서 생성
5. 계약+공급사 컨펌이 모두 완료되면 **"정산 대상"으로 자동 이동** (상담원이 별도로 옮길 필요 없음)

> 클릭 수 최소화 기준: 상담기록→견적서 1클릭, 견적→예약 1클릭, 예약→계약서/의뢰서 각 1클릭. 즉 문의 접수부터 정산 대상 등록까지 상담원이 반복 입력하는 항목이 없어야 합니다.

## 6. 개발 로드맵 (MVP → 2단계 → 장기 확장)

### MVP (1~2개월, 핵심만)
- 상담기록 + 견적서 (버전관리) + 예약(가예약/확정) 3단계만 우선 구축
- 계약서/예약의뢰서는 **PDF 양식 자동생성**(전자서명 없이 다운로드/카톡전송) 수준으로 시작
- 정산은 예약 건별 원가·판매가 입력 후 마진 자동계산 정도만 (엑셀 내보내기 지원)
- 상담원 3~5명 규모, Supabase 기반 웹 어드민으로 구축

### 2단계 (3~6개월)
- 계약서 **전자서명 연동** (예: 카카오 전자서명, 모두싸인 API)
- 예약의뢰서 **공급사 자동 발송**(이메일/API) + 회신 상태 추적
- 정산 자동화: 입금/출금 매칭, 미수금 알림, 월마감 리포트
- 상담원별/목적지별 실적 대시보드

### 장기 확장 (6개월~)
- 다른 여행사에도 판매 가능한 **SaaS형 ERP**로 확장 (테넌트 분리, 여행사별 상품/요율 커스터마이징)
- 리조트·랜드사와의 **실시간 재고·요금 연동(API)** → 견적 자동 산출
- 데이터 누적 기반 **가격 최적화/프로모션 추천** (인기 시즌·리조트 통계 활용)
- 고객용 모바일 웹으로 견적 확인, 계약서 서명, 결제까지 셀프서비스 확장

## 7. 예상 리스크 및 확인 필요 사항

- **환율/유류할증료 변동**: 견적 유효기한이 지나면 재계산이 필요 → 견적서에 유효기한·환율기준일 명시 필수
- **시즌 경계일 처리**: 성수기/비수기 경계에 걸친 일정은 요금이 이원화될 수 있음 → 마스터 시즌 테이블 설계 시 날짜 겹침 검증 로직 필요 (확인 필요)
- **공급사 정산 주기 상이**: 항공사(선결제) vs 랜드사(후정산) 등 조건이 달라 정산 모듈에서 공급사별 정산조건 컬럼 필수
- **전자계약서 법적 효력**: 사용할 전자서명 서비스가 전자문서법상 효력을 인정받는지 확인 필요 (확인 필요)

## 8. 다음 액션 제안

1. 현재 엑셀/수기로 관리 중인 **상담기록 양식과 견적서 양식**을 공유해 주시면, 이를 기준으로 실제 테이블 컬럼을 확정하겠습니다.
2. MVP 범위(상담-견적-예약)부터 Supabase 테이블 설계 및 관리자 화면 와이어프레임을 다음 단계로 진행할 수 있습니다.
3. 계약서/예약의뢰서 PDF 양식(현재 사용 중인 문서)이 있다면 함께 주시면 자동생성 템플릿에 반영하겠습니다.
